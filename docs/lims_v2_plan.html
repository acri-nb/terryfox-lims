Arbitrages du 13 août 2026 — intégrés dans tout ce qui suit

  • Le dépôt GitHub reste public et aucune réinitialisation de mot de passe n'est demandée : il n'y a pas eu d'incident de sécurité.
  • La V1 reste accessible après la bascule, pour comparer et pour consulter les données d'avant.
  • Aucune donnée ne doit être perdue, et des garde-fous doivent rendre la perte structurellement impossible plutôt que simplement improbable.
  • La v2 doit être élégante et moderne — l'interface actuelle n'est pas laide, elle est datée.

Ce qui est cassé aujourd'hui

Cinq problèmes trouvés en auditant le dépôt et le serveur. Aucun n'attend la v2 — tous sont actifs en ce moment. Les correctifs sont regroupés dans la section suivante.

1 · Il n'existe aucune sauvegarde

Ni tâche cron, ni timer systemd, ni rien dans /var/backups. La seule copie de db.sqlite3 qui existe ailleurs que sur ce disque est celle du dépôt git, et les deux derniers commits chore:update db sont espacés de neuf mois.

Autrement dit, aujourd'hui, la perte de la machine ou une fausse manœuvre coûterait jusqu'à neuf mois de saisie. C'est le point le plus grave de cette liste et il n'a rien à voir avec la v2.

2 · Supprimer un projet détruit tous ses cas, sans retour

Case.project est en on_delete=CASCADE. J'ai mesuré l'effet réel : supprimer P06_BC_lnRNA effacerait le projet et ses 256 cas, plus leurs commentaires. Il n'y a qu'une page de confirmation entre un clic et cette perte, aucune corbeille, et — voir le point 1 — aucune sauvegarde pour revenir en arrière.

3 · L'import CSV efface silencieusement les couvertures

Dans core/views.py, sur un cas existant, l'import fait case.dna_t_coverage = dna_t où dna_t vaut None quand la cellule est vide. Ré-importer un CSV partiellement rempli écrase donc les couvertures par NULL — et comme Case.save() recalcule le tier, les cas concernés basculent en FAIL sans un mot d'avertissement.

C'est actif aujourd'hui, sur le chemin d'édition en masse le plus utilisé. Correctif : cellule vide = inchangé, jamais effacé. C'est aussi ce que la v2 doit adopter comme règle générale.

4 · Le watchdog redémarrera le service pendant une migration

terryfox-lims-watchdog.timer a OnUnitActiveSec=5min, et watchdog.sh lance systemctl restart terryfox-lims.service dès que la sonde échoue. Pendant une fenêtre de maintenance où le service est volontairement arrêté, le watchdog le relance — potentiellement au milieu d'un migrate, donnant à trois workers gunicorn un accès en écriture concurrent à une base à moitié migrée. Restart=always dans l'unité aggrave le tout.

Le runbook de déploiement doit commencer par systemctl stop terryfox-lims-watchdog.timer.

5 · Un git checkout sur le serveur détruit les données vivantes

db.sqlite3 est suivi par git et perpétuellement modifié (gunicorn écrit dedans en continu). Un git checkout ., git restore ., git stash ou git reset --hard dans le répertoire de production remplace la base vivante par celle du dernier commit — soit un recul de près d'un an.

Chaque déploiement de ce plan implique une opération git dans ce répertoire.

Sur le dépôt public

Décision retenue : le dépôt reste public et il n'y a pas de réinitialisation des mots de passe. Voici ce que cela recouvre exactement, pour que le choix soit fait en connaissance de cause plutôt que par défaut.

Les hachages exposés sont du PBKDF2-SHA256 à 600 000 – 870 000 itérations, et les mots de passe distribués par le LIMS font 12 caractères tirés sur 62. Les casser est hors de portée pratique : la position « pas de réinitialisation » se tient. Il reste trois choses distinctes :

  • La SECRET_KEY publiée permet de forger une session Django valide sans connaître aucun mot de passe. C'est indépendant de la robustesse des mots de passe.
  • _generate_password() utilise random et non secrets — un générateur non cryptographique. Un mot à changer dans core/views.py.
  • db.sqlite3 publie 1329 cas de recherche avec leurs Biobank ID. C'est une question de gouvernance de données du consortium, pas de sécurité : cette diffusion a-t-elle été approuvée ? Elle n'est pas de nature technique et ne m'appartient pas.

Ces deux exigences ne s'opposent pas

Garder le dépôt public n'oblige pas à y publier .env et db.sqlite3. Sortir la base de l'arbre git — l'action n° 1 des garde-fous ci-dessous, demandée pour protéger les données — retire mécaniquement les données du dépôt. Le code reste public, la base cesse d'être publiée, et le git checkout destructeur du point 5 devient impossible. Une seule action sert vos deux contraintes.

Reste la SECRET_KEY : la faire tourner n'est pas une réinitialisation de mot de passe. Cela invalide les sessions ouvertes, donc chacun se reconnecte une fois avec son mot de passe actuel. Coût pour les 42 utilisateurs : une connexion. À vous de voir.

Les garde-fous sur les données

« Faire très attention » ne tient pas dans la durée. Huit mécanismes pour que la perte de données devienne structurellement impossible plutôt que simplement improbable — chacun rattrapant ce que le précédent laisse passer.

  1. La base vivante sort de l'arbre git

    db.sqlite3 déménage vers /var/lib/terryfox-lims/db.sqlite3 et settings_prod.DATABASES pointe dessus. Une ligne de configuration.

    Aucune commande git ne peut plus atteindre les données vivantes : la classe entière d'accidents du point 5 disparaît, et le dépôt cesse de publier la base sans cesser d'être public. Un instantané peut toujours être versionné volontairement, mais c'est alors un export délibéré, pas le fichier que gunicorn écrit en continu.

  2. Sauvegardes automatiques, vérifiées, avec rétention

    Un timer systemd horaire lance sqlite3 .backup — la sauvegarde en ligne cohérente, contrairement à un cp qui peut copier une base en cours d'écriture. Chaque archive est ouverte et comptée juste après création : si le nombre de cas ne correspond pas, l'archive est rejetée et une alerte part.

    Rétention : 48 horaires, 30 quotidiennes, 12 mensuelles. La base fait 656 Ko et se sauvegarde en 46 ms ; 286 Go sont libres sur le disque. Le coût est nul, l'absence actuelle n'a aucune excuse.

  3. Aucune migration sans point de restauration frais

    Le script de déploiement refuse de lancer migrate s'il n'existe pas une sauvegarde vérifiée datant de moins de cinq minutes, et il arrête le timer du watchdog en première instruction. Cette sauvegarde-là est conservée indéfiniment, étiquetée du numéro de migration.

  4. Contrôle d'invariants bloquant, avant et après

    Le même script compte les lignes de chaque table et la distribution des tiers avant, puis après. Les valeurs de référence sont connues : 1329 cas, 1550 commentaires, 15 projets, 42 utilisateurs, 552 A / 682 B / 95 FAIL. Tout écart non explicitement attendu par la migration déclenche un retour arrière automatique sur la sauvegarde de l'étape 3.

  5. Toute migration de données est réversible et testée dans les deux sens

    Chaque RunPython reçoit un reverse_code réel — pas noop. Avant tout passage en production, la migration est jouée en avant puis en arrière sur une copie de la base réelle, et l'on vérifie que l'état final est identique à l'état initial, octet par octet sur les colonnes concernées.

  6. Suppression douce partout

    Project, Case et Comment gagnent un champ deleted_at. Les vues de suppression le renseignent au lieu d'émettre un DELETE, et le gestionnaire par défaut filtre les lignes marquées. Rien ne quitte jamais la base par le chemin d'une interface web.

    La confirmation de suppression d'un projet doit annoncer le nombre exact de cas concernés et exiger la saisie du nom du projet. 256 cas ne partent pas sur un clic distrait.

  7. Une cellule vide ne signifie jamais « efface »

    Règle générale, pas seulement pour le correctif de l'import CSV : partout où une valeur peut arriver d'un fichier ou d'un formulaire, vide veut dire inchangé. Effacer une valeur devient un geste explicite. L'import v2 impose en plus une prévisualisation obligatoire — combien de créations, combien de mises à jour, quelles colonnes changent — avant d'écrire quoi que ce soit, le tout dans une seule transaction.

  8. Une restauration réellement répétée

    Une sauvegarde jamais restaurée n'est pas une sauvegarde. Avant la bascule v2, la procédure est exécutée pour de vrai : restaurer la veille dans une instance de test, ouvrir l'application, compter les cas. Puis une fois par trimestre.

Ce que ces huit points garantissent ensemble

Une erreur humaine sur l'interface est annulable (6, 7). Une erreur de migration est détectée puis annulée automatiquement (3, 4, 5). Une erreur d'exploitation ne peut plus atteindre le fichier (1). Et si tout échoue en même temps, la perte maximale est d'une heure (2), avec une procédure de retour qu'on aura déjà exécutée au moins une fois (8).

L'archive V1

La V1 reste consultable après la bascule. Le choix de conception qui rend cette promesse tenable dans le temps : la figer plutôt que la brancher sur les données vivantes.

Pourquoi figée, et non branchée sur la base courante

La tentation serait de garder les anciennes vues actives sur la base à jour, sous un préfixe /v1/. Ça ne tient pas : le code V1 lit des slugs de statut que la v2 renomme, il ignore les spécimens, et il ne connaît ni les tentatives archivées ni la suppression douce. Il afficherait donc des statuts vides et des cas incomplets — une V1 qui ment est pire que pas de V1. Et chaque migration future obligerait à maintenir deux jeux de vues sur un même schéma.

L'archive est donc une photographie : le code V1 tel qu'il est aujourd'hui, sur les données telles qu'elles étaient à l'instant de la bascule. C'est exactement ce que demande « retourner en arrière pour comparer » — un point de référence stable. Pour consulter les données courantes, ce sont les exports v2 qui répondent, et ils sont plus complets que ce que la V1 sait afficher.

Le montage

  • Une étiquette git v1.0-final sur le dernier commit avant migration, et un déploiement de ce tag dans /opt/terryfox-lims-v1/, indépendant du répertoire de travail.
  • Un instantané de la base pris juste avant la migration : /var/lib/terryfox-lims/v1-frozen.sqlite3, en chmod 444 et appartenant à un autre utilisateur que le service.
  • Un second service systemd sur un port distinct, exposé par le proxy en candig-lims.cair.mun.ca/v1/.
  • Les mêmes comptes et les mêmes rôles : personne n'a de nouveau mot de passe à retenir.

Lecture seule, en trois couches

Une seule barrière finit toujours par sauter. Trois, dont deux au niveau du système :

  1. Permissions du fichier — 444, propriétaire différent du compte de service.
  2. SQLite ouvert en lecture seule — NAME: 'file:/var/lib/terryfox-lims/v1-frozen.sqlite3?mode=ro' avec OPTIONS: {'uri': True}. Vérifié : Django lit bien les 1329 cas, et toute écriture est refusée par SQLite lui-même avec attempt to write a readonly database.
  3. Middleware — toute requête autre que GET ou HEAD est rejetée avec un message clair plutôt qu'une erreur 500.
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": "file:/var/lib/terryfox-lims/v1-frozen.sqlite3?mode=ro",
        "OPTIONS": {"uri": True},
    }
}

Ce que voit l'utilisateur

Un bandeau permanent en haut de chaque page de l'archive : « Archive V1 — lecture seule — données figées au 13 août 2026 », avec un lien de retour vers la v2. Les boutons de création, de modification et de suppression sont masqués, pas seulement désactivés — un bouton qui ne fait rien est plus déroutant qu'un bouton absent. Et dans la v2, un lien discret vers l'archive, pour que personne n'ait à retenir une URL.

Effet de bord utile

Cette archive est aussi la meilleure preuve que rien n'a été perdu. Après migration, on peut comparer côte à côte n'importe quel cas dans les deux systèmes. Elle est mise en place à l'incrément 5, avant la migration des spécimens — le filet est tendu avant le saut, pas après.

Les trois choses qui changent vraiment

Le reste des demandes sont des ajouts. Ces trois-là déplacent l'architecture.

Les « 3 types de spécimen » et la découpe de Daniel sont le même concept

La note de réunion demande un « type de spécimen : 1, 2 ou 3 ». Daniel demande, séparément, que « tumeur et normal soient des entités distinctes dans un cas, et que la tumeur soit séparée en ADN et ARN ». Ce sont les mêmes trois choses : Normal-ADN, Tumeur-ADN, Tumeur-ARN.

Et elles correspondent exactement, une pour une, aux trois colonnes de couverture actuelles (dna_n_coverage, dna_t_coverage, rna_coverage). La migration est donc sans perte, et les seuils de tier se transposent sans changer une valeur. Un seul concept nouveau à introduire dans l'interface, pas deux.

Le statut descend au niveau du spécimen — mais l'interface doit continuer à parler « cas »

« Suivre ces choses indépendamment même si elles partagent le même case ID » signifie que le statut est une propriété du spécimen. Mais si on s'arrête là, l'action la plus fréquente du système — un technicien qui fait avancer un cas d'un cran — passe de un menu déroulant à trois.

La v2 garde donc un statut de cas, dérivé des spécimens, exactement comme le tier est déjà dérivé des couvertures. Le patron existe déjà dans ce code, l'équipe le connaît.

La biobanque cesse de saisir des identifiants

L'ACC devient généré par le LIMS, et le Biobank ID devient le champ par lequel on cherche. C'est un renversement : aujourd'hui l'unique champ de recherche de la page projet interroge Case.name, c'est-à-dire l'ACC. Si on ne change que la génération, taper « N-BBN 42 » dans la recherche ne renverra rien — la demande phare serait ratée par omission.

Trois contradictions à trancher

Les demandes se contredisent sur trois points. Voici la résolution proposée pour chacun.

Le même ACC, mais des identifiants uniques

La re-soumission demande « un nouveau cas réutilisant le même ACC ». La prévention des doublons demande que « le LIMS bloque les identifiants dupliqués ». Littéralement, l'une interdit l'autre.

Résolution : l'unicité porte sur les cas actifs. Un index unique partiel conditionné sur is_archived = False autorise exactement un cas actif par ACC, pendant que les tentatives archivées partagent librement le même. Comportement vérifié sur SQLite 3.45 : insérer un second cas actif avec l'ACC 42 est bloqué ; l'ACC 42 tentative 2 après archivage de la tentative 1 est accepté. 

UniqueConstraint(fields=["acc_number"], condition=Q(is_archived=False),
                 name="uniq_active_acc")

Le suivi par spécimen, mais une interface qui reste simple

Si Case.status disparaît, huit vues, deux formulaires de filtre, l'import CSV, l'export CSV et tous les badges de statut cassent — et le technicien passe de un à trois menus déroulants pour l'action la plus courante du système.

Résolution : Specimen.status est la seule chose qu'on écrit ; Case.status survit comme miroir stocké en lecture seule, recalculé à chaque écriture — le même patron que Case.tier. Sur la fiche de cas, un menu « Statut du cas » applique à tous les spécimens en un clic ; les trois menus individuels sont l'exception, repliés sous un « Suivre séparément ».

Un cas n'a pas toujours trois spécimens

Si l'on force les trois spécimens sur chaque cas et que le statut du cas est celui du spécimen le moins avancé, alors P01_Lung — ctDNA (150 cas, ADN circulant) et P10_Prostate (32 cas, aucune valeur d'ARN) afficheraient « Case Created » à perpétuité, même une fois l'analyse ADN terminée. Un PI ouvrant P01 l'an prochain verrait 150 cas apparemment jamais commencés.

Résolution : un cas porte 1 à 3 spécimens, et le rollup ne considère que ceux qui existent. C'est aussi la lecture littérale de « l'utilisateur choisit parmi les types 1, 2 ou 3 ».

Le modèle de données

Un seul modèle nouveau porte l'essentiel de la v2. Tout le reste est additif.

Ce qui est ajouté

  • Specimen — case, specimen_type (les trois types), status, coverage, external_id. Unicité sur (case, specimen_type).
  • Case.acc_number (entier, triable et contraignable) à côté de Case.name qui reste la chaîne ACC-%04d affichée partout.
  • Case.attempt, Case.is_archived, Case.superseded_by pour la re-soumission.
  • Case.is_priority, Project.kind (recherche / cas référés).
  • IdentifierSequence — une ligne, un compteur, pour l'allocation des ACC.
  • StatusEvent et BatchOperation — la traçabilité qui rend l'annulation des changements en lot possible.

Ce qui n'est pas touché

Les trois colonnes de couverture restent sur Case, en miroir des spécimens. Conséquence : calculate_tier() n'est pas modifié d'un caractère, les templates de liste continuent de fonctionner, l'export CSV aussi, et le retour arrière consiste à supprimer les lignes Specimen. Les supprimer sera un chantier séparé, plus tard, protégé par un test de référence.

Critère de non-régression de la migration

Après le backfill, la distribution des tiers doit être exactement 552 A / 682 B / 95 FAIL, et aucun statut de cas ne doit avoir changé. Une répétition à blanc du backfill donne aujourd'hui 0 changement de tier et 0 changement de statut. Si ce n'est pas le cas le jour J, on annule.

La génération des ACC

Max(acc_number) + 1 est en situation de course avec trois workers gunicorn, et select_for_update() lève NotSupportedError sur SQLite. Le motif correct est d'écrire avant de lire, ce qui prend le verrou d'écriture de SQLite dès la première instruction : 

with transaction.atomic():
    IdentifierSequence.objects.filter(key="acc").update(
        last_value=F("last_value") + n)
    last = IdentifierSequence.objects.get(key="acc").last_value
    return range(last - n + 1, last + 1)

Les statuts

Dix statuts en trois étapes. Le regroupement n'est pas décoratif : il porte l'ordre, ce que dix badges de couleurs différentes ne savent pas faire.

ÉtapeStatutsQui les pose
Biobanque Case Created défaut · Sent to Sequencing Center Biobanque
Séquençage Received · QC complete · Library complete · iSeq finished · Sequencing Complete Centre de séquençage
Bio-informatique Transferred to CAIR · Analyzing · Analysis complete CAIR

Comment ça s'affiche

Trois micro-barres empilées dans une seule cellule de tableau, préfixées N / D / R. Les segments remplis indiquent l'étape atteinte. Un technicien voit « deux terminés, un en attente » sans lire, là où un badge unique replierait l'information sur la pire valeur.

N · ADN Analysis complete
D · ADN Analysis complete
R · ARN Sequencing Complete

Le statut du cas est celui du spécimen le moins avancé, et il se libelle explicitement — Sequencing Complete · en attente de Tumeur (ARN) — plutôt que de laisser croire que le cas entier stagne.

Les 469 cas sans équivalent

incomplete (428) et unknown (41) n'existent dans aucune des trois étapes. Les inventer serait perdre l'information ; les mapper arbitrairement ferait apparaître 469 cas plus avancés ou moins avancés qu'ils ne sont.

La donnée tranche à moitié la question : 385 des 428 cas incomplete ont leurs deux couvertures ADN et pas d'ARN, et leurs commentaires disent littéralement « Needs Normal Top-Up », « No DNA Normal fastq ». incomplete signifie donc « ARN en attente » — ce que le modèle par spécimen exprime nativement, sans statut supplémentaire.

Proposition : conserver les deux valeurs comme statuts dépréciés (« Unknown (pre-V2) »), invisibles dans les menus de saisie mais visibles dans les filtres, et les vider projet par projet avec l'outil de changement en lot — c'est exactement l'usage pour lequel cet outil a été demandé.

Les écrans

Ce qui change, écran par écran, et pourquoi.

Page projet — le chantier principal

La grille de cartes devient un tableau dense, trié, paginé. C'est la condition d'existence des cases à cocher : cocher 40 cases parmi 128 rangées de cartes, sans tout-sélectionner ni tri ni sélection par plage, ne remplace pas l'aller-retour CSV — ça le remplace par pire.

  • Colonnes : case à cocher · ACC · Biobank ID · les trois micro-barres · Tier · dernière mise à jour.
  • Identifiants en police à chasse fixe. ACC-0142 et ACC-0412 se distinguent en mono, pas en proportionnel.
  • En-tête collant, tout-sélectionner, sélection par plage avec Maj-clic.
  • Une seule zone de recherche libellée « ACC ou Biobank ID », interrogeant les deux champs.
  • Filtres : statut groupé par étape, tier, et une bascule « Prioritaires uniquement ».
  • Le N+1 disparaît : deux annotations remplacent 512 requêtes.

La barre d'action en lot

Elle apparaît quand au moins une ligne est cochée, et porte deux menus : appliquer à (tous les spécimens / Normal / Tumeur-ADN / Tumeur-ARN) et nouveau statut. Sans le premier menu, « passer 40 cas à Sequencing Complete » est ambigu dès lors que le statut vit sur le spécimen.

Chaque application s'exécute dans une transaction, journalise un BatchOperation et une ligne par spécimen touché, puis revient sur la même URL filtrée avec une bannière Annuler qui ne remet en arrière que les spécimens encore à la valeur qu'on venait de poser.

Fiche de cas

  • En-tête d'identité : ACC en gros, Biobank ID, projet, drapeau prioritaire.
  • Un menu « Statut du cas » + bouton, qui applique aux spécimens présents. Les trois menus individuels sont repliés.
  • Le panneau des spécimens affiche l'unité dans le champ lui-même (X pour l'ADN, M pour l'ARN) — un help-text partagé entre trois lignes identiques de formulaire ne suffit pas à empêcher une saisie en mauvaise unité, qui produirait un Tier A erroné.
  • Historique des soumissions : les tentatives précédentes, avec le nombre de commentaires qu'elles portent — c'est généralement dans ces commentaires que se trouve la raison de la re-soumission.
  • Sur un cas archivé : bandeau en lecture seule « Remplacé par la tentative 2 », formulaires masqués. Sinon un technicien arrivant par un vieux lien éditera un cas mort.

Création en lot

Le formulaire actuel génère des noms par intervalle numérique. Avec l'ACC généré automatiquement, cette logique disparaît — mais si on la remplace par un simple champ « nombre de cas », le technicien obtient 50 cas anonymes puis doit ouvrir 50 pages pour saisir les Biobank ID.

À la place : une zone de texte, un Biobank ID par ligne. Le LIMS alloue les ACC et crée les cas déjà porteurs de leur identifiant cherchable. Le patron existe déjà dans ce code — BatchUserCreateForm fonctionne exactement ainsi.

Exports

  • Par projet : un CSV large, une ligne par cas, avec un bloc de colonnes fixe pour chacun des trois spécimens. C'est ce format-là qu'un PI croise avec sa feuille clinique par RECHERCHEV sur le Biobank ID.
  • Export complet : une archive ZIP construite avec la bibliothèque standard — cases.csv, specimens.csv, comments.csv, cases_archived.csv, et un README.txt qui décrit les colonnes.
  • Les tentatives archivées vont dans un fichier séparé, jamais mélangées derrière une colonne d'état : une erreur de filtre gonflerait un effectif publié.
  • Chaque fichier enfant porte (acc_id, attempt) comme clé de jointure. Joindre sur l'ACC seul après une re-soumission dupliquerait les lignes de la tentative 1 sur la tentative 2.

Les règles d'ergonomie

Le critère au-dessus de tous les autres. Chacune de ces règles répond à une manière concrète dont la v2 pouvait rendre le système plus pénible qu'aujourd'hui.

  • Faire avancer un cas reste un seul menu déroulant. Le suivi par spécimen est une option repliée, jamais le chemin par défaut. C'est l'action la plus fréquente du système ; elle ne doit pas tripler.
  • Aucun cas n'est forcé à trois spécimens. Sinon 182 cas de P01 et P10 afficheraient « Case Created » à vie.
  • Un seul champ de recherche, qui cherche l'ACC et le Biobank ID. Plus une recherche globale dans la barre de navigation, tous projets confondus.
  • Créer 50 cas, c'est coller une liste. Pas 50 chargements de page.
  • Un doublon nomme le cas en conflit. « Le Biobank ID N-BBN 42 est déjà utilisé par ACC-0311 dans P06 — ouvrir ce cas ? », jamais Constraint "uniq_active_biobank_id" is violated.
  • Toute action en lot est annulable. Et la confirmation nomme le nombre de cas touchés.
  • Rien ne change de place. Barre de navigation, fil d'Ariane, action principale en haut à droite. Toutes les URL et tous les paramètres ?name=, ?status=, ?tier=, ?project_lead= continuent de fonctionner : les signets des utilisateurs avancés ne cassent pas.
  • L'unité s'affiche dans le champ. X pour l'ADN, M pour l'ARN, en suffixe visible — pas dans un help-text répété trois fois.
  • Les statuts dépréciés disparaissent des menus de saisie mais restent dans les filtres. Sinon le personnel ne peut plus retrouver les 469 cas qu'on lui demande de reclasser.
  • Jamais la couleur seule. Chaque état porte aussi un texte ou une forme. Contraste minimum 4,5 : 1, cibles de clic d'au moins 24 px, focus visible au clavier.

Le design

L'interface actuelle n'est pas laide, elle est datée — d'une façon précise, nommable et réparable. L'objectif de la v2 est qu'elle soit élégante, et l'archive V1 permet d'y aller franchement.

Le diagnostic

templates/base.html contient environ 265 lignes de CSS en ligne qui reprennent la palette Flat UI Colors de 2013 — #2c3e50, #3498db, #e74c3c, #1abc9c, #9b59b6, #2ecc71. Trois détails signent l'amateurisme plus que la palette elle-même :

  • .card:hover { transform: translateY(-5px) } — toutes les cartes lévitent, y compris celles qui ne sont pas cliquables. C'est le signal « kit de template » le plus fort de l'application.
  • Une ombre portée sur chaque surface, y compris les simples conteneurs de mise en page.
  • Une icône FontAwesome collée à chaque lien, chaque titre, chaque bouton — neuf rien que dans la barre de navigation. Environ 500 Ko de police pour une quinzaine de glyphes réellement utilisés.

Ce qu'on s'interdit

« Éviter les slops AI » se traduit par une liste de choses bannies, écrite une fois pour toutes : dégradés violet-vers-bleu, glassmorphisme, emoji en guise d'icônes, section d'accueil surdimensionnée, cartes statistiques arc-en-ciel, texte d'accueil du type « Bon retour parmi nous ! », illustrations décoratives, Inter ou Space Grotesk comme police « par défaut sûre », et mode sombre non demandé.

Ce que « moderne » veut dire ici

Pas des effets. Un outil de laboratoire paraît moderne quand la densité est maîtrisée, quand la typographie est choisie plutôt que subie, quand chaque état — vide, en cours, en erreur, confirmé — a été dessiné, et quand la couleur porte du sens au lieu de décorer. C'est le contraire d'un habillage : c'est du travail sur la lisibilité.

La direction retenue

  • Une vraie identité typographique. IBM Plex Sans pour l'interface et IBM Plex Mono pour tous les identifiants et toutes les valeurs numériques — libres, auto-hébergées, d'origine industrielle et scientifique. Elles donnent un caractère net que la pile système n'a pas, et elles évitent délibérément Inter et Space Grotesk, devenues la signature du « généré ». ACC-0142 et ACC-0412 se distinguent en mono, pas en proportionnel : c'est le changement typographique qui a le plus de valeur pratique ici.
  • Bordures, pas d'ombres. Un filet de 1 px, zéro ombre au repos. L'ombre est réservée aux couches réellement flottantes — menu, modale, en-tête collant. Un système à filets s'imprime, une ombre non.
  • Une grille de 4 px, tenue partout. L'espacement est ce qui sépare le plus visiblement une interface soignée d'une interface fonctionnelle. Une échelle typographique fermée, et rien en dehors.
  • Badges teintés. Fond clair, texte foncé de la même teinte, filet de 1 px. Mesuré : 5,20 : 1 pour le vert, 5,66 : 1 pour l'ambre, 5,59 : 1 pour le rouge, contre 2,10 à 3,82 : 1 aujourd'hui. Les badges cessent aussi de crier dans un tableau de 40 lignes.
  • Sémantique du tier corrigée. A vert, B ambre, FAIL rouge. Aujourd'hui A est rouge et FAIL est gris : un PI qui survole un projet voit un mur de rouge et lit une catastrophe.
  • Le statut est une progression, pas dix teintes. Dix couleurs n'ont pas d'ordre ; on ne peut pas deviner si « QC complete » précède « Library complete ». Une barre à segments l'encode sans lecture.
  • La page d'accueil devient un tableau de bord, pas une liste de compteurs. Répartition par étape, distribution des tiers, cas prioritaires en attente : de vraies petites visualisations, sobres et monochromes, qui répondent en un coup d'œil à « où en est le consortium ». C'est le gain de modernité perçue le plus fort du chantier, et il est aussi utile.
  • Les états intermédiaires sont dessinés. Listes vides avec une action proposée, indicateur d'attente sur les opérations en lot, confirmations en bandeau, messages d'erreur qui nomment le problème et la sortie. C'est précisément ce dont l'interface actuelle est dépourvue, et ce qui la fait paraître inachevée plus que datée.
  • Mouvement discret. 120 ms sur les seuls éléments interactifs, et prefers-reduced-motion respecté. Aucune animation décorative — c'est là que le « moderne » bascule dans le clinquant.
  • Bootstrap conservé, mais plus aucun composant à son apparence d'origine. Il porte la grille, les menus et le pack crispy-forms des 18 templates : le retirer serait une réécriture déguisée en changement de style. En revanche, si un bouton, un tableau ou un formulaire ressemble encore à du Bootstrap par défaut à la livraison, le travail n'est pas fait. Le bloc <style> en ligne disparaît au profit d'un unique static/css/lims.css piloté par jetons.
  • Une feuille d'impression. Les PI impriment les fiches de cas.

Ce qui ne bouge pas, malgré tout

L'élégance ne s'achète pas en réorganisant l'application. La barre de navigation reste en haut, le fil d'Ariane garde son ordre, l'action principale reste en haut à droite, et toutes les URL et tous les paramètres de filtre continuent de fonctionner. Une barre latérale serait plus « moderne » sur une capture d'écran et coûterait un réapprentissage à 42 personnes pour cinq destinations — on ne l'échange pas contre ça. Le seul ajout dans la barre est le champ de recherche global, qui sert aussi la recherche par Biobank ID.

Pas de mode sombre en v2.0. Personne ne l'a demandé, il double la surface de vérification visuelle sur un projet qui n'a pas encore de tests, et un mode sombre non sollicité fait justement partie des signes du travail généré. C'est une décision, pas un oubli — il pourra venir ensuite.

Deux pièges de déploiement sur cette étape

settings_prod.py utilise CompressedManifestStaticFilesStorage : tout chemin {% static %} absent de staticfiles.json lève une ValueError et renvoie une 500. Redémarrer le service sans collectstatic après avoir ajouté lims.css met tout le site à terre pour les 42 utilisateurs.

Et templates/base.html n'a pas de {% load static %} : ajouter une balise {% static %} sans cette ligne fait lever une TemplateSyntaxError sur toutes les pages, page de connexion comprise — plus personne ne peut entrer.

Le renommage des statuts casse aussi le style au passage : base.html code en dur neuf règles .badge-<slug> et neuf règles .case-<slug> sur les slugs actuels. Après migration, les 855 cas completed deviennent analysis_complete et perdent leur couleur. La parade est d'arrêter de coder la couleur sur le slug : quatre classes d'étape remplacent dix classes de statut, ce qui fait aussi quatre couleurs à apprendre au lieu de dix.

Sur l'infrastructure

Rester sur SQLite. Mesuré : trois écrivains et trois lecteurs concurrents produisent 0 erreur de verrou, en mode delete comme en mode WAL, avec un p95 de 4 à 5 ms. La base entière fait environ 650 Ko et se sauvegarde en 46 ms. Activer WAL, les transactions IMMEDIATE et un délai d'attente de 20 s suffit ; PostgreSQL n'est pas justifié à cette échelle.

Ce qui vous appartient

Six questions que le code ne peut pas trancher. Les recommandations ci-dessous ont été acceptées le 13 août 2026 et sont désormais la ligne de conduite ; elles restent documentées ici avec leur justification, pour qu'on sache pourquoi si on veut les rouvrir.

Seul point encore ouvert

Faire tourner ou non la SECRET_KEY. Ce n'est pas une réinitialisation de mot de passe : chacun se reconnecte une fois avec son mot de passe actuel. Sans rotation, la clé publiée continue de permettre la forge de sessions valides. Coût d'une reconnexion pour 42 personnes contre cette exposition — la décision vous revient, elle ne bloque aucun incrément.

D1 · Combien de spécimens par cas ?

446 cas n'ont pas de valeur d'ARN, et P01_Lung est de l'ADN circulant où un spécimen d'ARN tumoral ne sera peut-être jamais prélevé.

Recommandation : le type de spécimen se coche à la création, comme le demande la note de réunion. Pour la migration, créer les trois spécimens partout sauf pour les projets que la biobanque désigne comme sans ARN. Supprimer des spécimens en trop est une requête ; en recréer 446 à la main ne l'est pas.

D2 · Que deviennent les 469 cas incomplete et unknown ?

Recommandation : les garder comme statuts dépréciés et les vider avec l'outil de lot, projet par projet, avec la biobanque dans la pièce. Si le consortium veut une table rase au jour 1, le mappage le moins inventif est incomplete → Sequencing Complete (ADN fait, ARN en attente) et unknown → Case Created. La valeur d'origine est conservée dans tous les cas.

D3 · Le Biobank ID doit-il être unique globalement, ou seulement par projet ?

Zéro collision aujourd'hui — mais c'est de la chance, pas de la conception : P08_CRC utilise des identifiants numériques nus de 5 à 849, et P09_BC_EV de 102 à 850. Deux projets partagent un même espace de numérotation. Le jour où P09 enregistre son patient 300 alors que P08 a déjà un 300, une contrainte dure bloque la technicienne sur le vrai identifiant du patient.

Recommandation : unicité dure sur l'ACC, qui est généré par le LIMS et donc gratuite. Contrôle souple sur le Biobank ID : « cet identifiant existe déjà dans P08_CRC (ACC-0742). Même patient ? [Ouvrir] [Non, créer quand même] ». La demande dit « ne peut plus être créé dans deux projets par erreur » — c'est une prévention d'erreur, pas un axiome d'unicité.

D4 · La re-soumission porte-t-elle sur le cas entier ou sur un spécimen ?

Recommandation : au niveau du cas, comme demandé — un bouton, un avant et un après clairs — avec une case « le Normal est encore bon » qui reporte le spécimen valide et sa couverture dans la nouvelle tentative. Distinguer par ailleurs le top-up (un spécimen recule d'un cran sur le même cas) de la re-soumission (nouveau prélèvement physique après échec).

D5 · Les cas prioritaires remontent-ils en tête de liste ?

Recommandation : oui, épinglés en tête, plus un marqueur ambre et un filtre dédié. Un cas urgent sorti de l'écran par le défilement vide la demande de sa substance. Revenir en arrière est une ligne de code si le personnel dit ne plus retrouver ses ACC en balayant la liste.

D6 · Qui peut extraire un export consortium complet ?

Le fichier contient les données de tous les projets de tous les groupes. Recommandation : superutilisateurs uniquement, avec journalisation de qui l'a extrait et quand. Les PI gardent l'export de leur propre projet en un clic.

Chiffres mesurés sur db.sqlite3 et sur le serveur de production le 13 août 2026. Les recommandations engagent une lecture du code ; les valeurs par défaut proposées s'appliquent faute de décision contraire du consortium.
