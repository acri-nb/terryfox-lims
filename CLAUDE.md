# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

TerryFox LIMS — a Django 5 Laboratory Information Management System for ACRI tracking research projects, cases, sequencing coverage and tier classification. Server-rendered Django templates (Bootstrap 5 + crispy-forms), SQLite, deployed with Gunicorn over HTTPS behind systemd.

## Commands

All deployment scripts activate the conda env named `django` (`source ~/miniconda/etc/profile.d/conda.sh && conda activate django`). Use it for local work too.

```bash
# Development server (uses terryfox_lims/settings.py, DEBUG=True)
python manage.py runserver

# Migrations
python manage.py makemigrations && python manage.py migrate

# Tests — core/tests.py is an empty stub; there is no real Django test suite yet
python manage.py test core
python manage.py test core.tests.SomeTestCase.test_method   # single test

# Tier logic check — standalone script, NOT a Django test (calls django.setup() itself)
python test_tier_criteria.py

# Recompute tiers on all existing cases after changing tier thresholds
python update_tier_b_criteria.py

# Pre-flight check of production settings (DEBUG, SECRET_KEY, ALLOWED_HOSTS, SSL...)
python check_production.py

# Static files (production settings required)
python manage.py collectstatic --noinput --settings=terryfox_lims.settings_prod
```

Production (systemd units already installed: `terryfox-lims.service`, `terryfox-lims-watchdog.timer`):

```bash
sudo systemctl {status,restart,stop} terryfox-lims.service
sudo journalctl -u terryfox-lims.service -f
tail -f /var/log/terryfox-lims/{access,error,watchdog}.log
```

The service runs `gunicorn_start_robust.sh` → `gunicorn terryfox_lims.wsgi_prod:application` bound to `0.0.0.0:443` with self-signed certs from `/root/ssl/`. Requires root (port 443). The other `start_*.sh` scripts are older/alternative launch paths kept around; prefer the systemd service.

## Architecture

Single Django app `core` plus project package `terryfox_lims`. Everything meaningful lives in five files:

- `core/models.py` (~160 lines) — ProjectLead → Project → Case → {Accession, Comment}
- `core/views.py` (~880 lines) — all function-based views, no CBVs
- `core/forms.py` — ModelForms + the batch/CSV/filter/user-management forms
- `core/urls.py` — flat URL table for the whole app
- `templates/core/` — one template per view

### Two settings modules

`terryfox_lims/settings.py` (dev: DEBUG=True, hardcoded insecure SECRET_KEY, no whitenoise) and `terryfox_lims/settings_prod.py` (DEBUG=False, reads `.env` via python-decouple, HSTS/secure cookies, whitenoise, `django_extensions`, `WSGI_APPLICATION = terryfox_lims.wsgi_prod`). They are **duplicated files, not layered** — a settings change usually has to be made in both. `ALLOWED_HOSTS` differs between them.

### Tier is derived, never user-supplied

`Case.save()` unconditionally overwrites `self.tier` with `calculate_tier()` from the coverage values (`dna_t_coverage`, `dna_n_coverage`, `rna_coverage`). Setting `tier` in a form, fixture, or the admin has no effect. Rules: FAIL if either DNA value is missing or <30X; A if DNA(T)≥80 & DNA(N)≥30 & RNA≥80; B otherwise when DNA(N)≥30 and DNA(T)≥30. Changing thresholds does **not** retroactively update rows — existing cases must be re-saved (see `update_tier_b_criteria.py`). Criteria history is in `docs/TIER_CRITERIA_UPDATED.md` and `docs/CHANGELOG_TIER_UPDATE.md`.

### Permissions: two different mechanisms

- Project/Case/ProjectLead views use Django model permissions via `@permission_required('core.add_case', ...)`. Access is granted by membership in the `viewer` (read-only) or `editor` (CRUD) groups. Both groups are auto-created by a `post_migrate` signal at the bottom of `core/models.py`, but their *permission assignments* are not code-managed — they are set in the admin / DB.
- User-management views (`user_list`, `user_create`, `batch_user_create`, `user_update`, `user_delete`) bypass that and check `request.user.is_superuser` inline. Role is inferred from group membership; passwords are auto-generated by `_generate_password()` and shown once.

### Dead / unwired code — verify before touching

- `core/api_views.py`, `core/api_urls.py`, `core/serializers.py` implement a DRF + SimpleJWT REST API, but `core/api_urls` is **not included** in `terryfox_lims/urls.py` and neither `djangorestframework` nor `djangorestframework-simplejwt` is installed or in `requirements.txt`. Importing these modules raises `ModuleNotFoundError`.
- `templates/react_app.html`, `templates/react_app_production.html`, `start_react_dev.sh`, `start_production_react.sh`, `docs/README_REACT.md` reference a `frontend/` React app that **does not exist in the repo**.

Treat the Django template UI as the only live frontend.

### CSV import/export

`csv_case_import` (`core/views.py`) accepts headers `CaseID,Other_ID,Status,DNAT,DNAN,RNA`, upserts by case name within the project, and maps human-readable status labels to the `STATUS_*` slugs. A template CSV lives in `static/csv/`.

## Repo conventions

- `db.sqlite3` is **committed to git** and routinely updated (`chore:update db` commits). It is the live data, not a fixture — be careful with any command that writes to it.
- `.env` is committed and holds production secrets/config keys read by `settings_prod.py`.
- Model verbose names and user-facing strings use `gettext_lazy as _`; there are no translation catalogs — it is convention only.
- Comments and script output are a mix of English and French.
